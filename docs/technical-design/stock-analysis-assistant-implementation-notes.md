## 2. 代码结构与职责

```
src/assistant/
├── __init__.py            版本与包说明
├── enums.py               阶段码 / 守卫序 / 动作 / 风险码 / 规则号（唯一真值）
├── domain.py              输入输出 dataclass（Bar / StockView / RiskSignal / PlanBranch …）
├── config/
│   ├── presets.py         45 项参数注册表 + 三档预设 + 契约校验
│   └── overrides.py       ParamSet（基线+覆盖）、param_hash、变更记录
├── engine/
│   ├── indicators.py      SMA / 斜率 / 分位 / 箱体 / 关键价位（纯函数）
│   ├── stage.py           阶段判定 S0–S5 + 连续 N 日防抖
│   ├── stage_gate.py      阶段门 S5.5（8 条改写规则 + 只收紧断言）
│   ├── scoring.py         技术面主导评分 + 决策表 + 档位缓冲
│   ├── risk.py            风险 7 类 / 三级联动 / 同类合并
│   ├── market.py          M1 大盘环境（指数日线 → 涨跌 + 2×2 档位）
│   ├── sector.py          板块强度三档（板块指数日线 → 2×2；rs_t 仅展示）
│   ├── plan.py            条件计划（阶段模板 + 同向过滤 + 股数 + 硬上限）
│   └── guard_chain.py     守卫链 S0→S6 主入口（留痕 GuardTrace）
├── versioning.py           calc_version 指纹（规则集 + 参数 + 分数带）
├── render/
│   ├── icons.py            图标语义表（固定映射，三处共用）+ 纯文本剥离
│   ├── review.py           T 日复盘（T-1 计划对照 T 日行情，只读）
│   └── feishu.py           七段图标化渲染（两档密度 + 超长按序降级）
├── pipeline.py             装配链：ensure_snapshot / payload / generate（幂等）
├── llm.py                  文案层：白名单 → 生成 → 校验 → 缓存/降级（默认关闭）
├── stage_text.py           阶段打法/允许/禁止/切换的唯一出处（飞书 ⑤ 段与 Web 详情共用）
├── inbound.py              飞书入站四项：白名单/二次确认/生效时点/只读查询/笔记
├── backtest.py             条件计划回合模拟：触发/成交/出场/成本 + 胜率口径
├── backtest_replay.py     历史计划回放驱动：逐日切片→守卫链→回合→统计（可续跑）
├── strategies.py           战法启停清单（§5.12.3）：静态登记 → calc_version
├── notify.py               发送接线：payload → 既有通知链（route_type / 去重键 / 纯文本降级）
├── config/
│   ├── presets.py          45 项参数注册表 + 三档
│   ├── overrides.py        单项覆盖 + param_hash + append-only 变更
│   └── service.py          配置 API 唯一入口：env 初始 → L4 生效、下一次快照生效
├── mode.py                 main.py 入口判定（零依赖，未启用时不加载取数栈）
├── service.py              运行时装配 + 调度循环（main.py 显式 opt-in）
├── data/
│   ├── models.py          21 张 assistant_ 表（L1 / L3 / L4 + 投递台账 + 防抖状态）
│   └── storage.py         L1 幂等写入、周月线聚合、L3 append-only、L4 变更重放、投递台账
└── scheduling/
    ├── cron.py            5 字段 cron 解析与匹配（自实现，零依赖）
    ├── config.py          时点配置（HH:MM 简写 + cron 混用）、按日触发计划
    ├── gate.py            交易日门控（fail-closed，日历在 decide 内延迟 import）
    ├── delivery.py        多时点同源投递、去重台账、同源不变量校验
    └── runner.py          一次 tick 的完整节拍（门控 → 排程 → 生成 → 投递）
```

**依赖方向**：`enums` ← `domain` ← `config` / `engine` ← `data` ← `scheduling`。
`engine` 不 import `data`；`scheduling` 全程**只用标准库**（cron 自实现、时区用
`zoneinfo`），交易日历只在 `TradingDayGate.decide()` 内部延迟 import，因此调度层可在
无 pandas / 无 SQLAlchemy 的解释器下单独测试与运行（已实测）。

### D-8 逗号双重语义：配置串不能「先按逗号切」（**实测踩坑并修复**）

- 配置里逗号既是 `HH:MM` 列表分隔符（`08:00,20:00`），也是 cron 字段的列表运算符
  （`0 8,20 * * *`）。第一版按逗号整体切分，把 `0 8,20 * * *` 切成 `0 8` + `20 * * *`
  两条非法项，**静默回退成默认 20:00**，用户配的 8 点/20 点双推完全没生效。
- 现实现：先按**空格分词**，再按「片段是否含冒号」区分——含冒号的是 `HH:MM` 候选，
  不含冒号的是 cron 字段（同一 token 内的多个片段用逗号拼回一个字段）。
- 已加回归用例：`0 8,20 * * *`、`08:00,0 20 * * 1-5`、`0 20 * * 1-5` 三种混用形态。

  与 B50 ③「当日快照只生成一次」冲突）；**文案指纹 `fingerprint` 含提示词版本 + 模型 +
  temperature**，随文案一起存进 `assistant_llm_text_cache`，同快照可复现同一段文案。
- `assistant_llm_text_cache` 增加 `fingerprint` / `usage_json` 两列（`create_all` 不改老表，
  本地开发库需重建——与 D-13 同一处理方式）。
- 三处已全部接上：飞书 ② 段摘要（`llm_summary` 可选参数，默认 None 时输出逐字不变）、
  个股一句话、大盘总结（`position="market"`，Web Tab A 展示）。
- **三处都在 `pipeline.payload` 一次写完**：详情页与 Web 只 GET 缓存，不在读接口里现调模型
  ——否则第一次打开页面与飞书推送会是两段不同的文案，违反「同快照只生成一次」。
  代价是 20:00 那次要串行调 `1 + 1 + N` 次；N 受 `ASSISTANT_LLM_MAX_CALLS_PER_DAY`（默认 20）
  约束，超出的标的直接落规则模板，不会把推送拖成不可控长尾。
- 后端复用 `src/llm/backend_factory`，主流程 Analyzer 的渠道 router 没有直接复用（它绑定
  Analyzer 实例），M14 实测完成前默认关闭；渠道不可用时一律规则模板降级，不阻塞推送。
- 超时用线程池 + `future.result(timeout=)` 硬截断，**不在 `__exit__` 里等后台线程**，否则
  卡死的渠道会拖住 20:00 推送；后端自身仍应设 timeout。
- 每日调用上限是**进程内软限制**（重启归零）；硬上限依赖「同快照同位置只生成一次」的
  缓存与每日快照数量。仓库目前没有按 $/token 的成本预算机制，本增量不假装做了金额封顶。

### D-27 历史计划回放驱动（D-24 收口）：逐日切片的五条硬约束

- 落点：`src/assistant/backtest_replay.py`（纯逻辑，不联网）+ `scripts/assistant_backtest_replay.py`
  （批处理入口）。**回合口径一个字没改**：成交价、跳空、T+1、同日先止损、未闭合不计分母、
  样本 ≥30 才给胜率，全部复用 `backtest.simulate_rounds` / `summarize_rounds`。
- **① 不碰未来数据**：每天把 K 线截到 T 再进守卫链；传给守卫链的交易日历也只给到 T
  （未来日历虽不含价格，也没必要提前泄露）。**T 日 K 线未发布就跳过该标的**
  （`skipped_stale_bars`），绝不拿 T-1 的结论冒充 T 日。
- **② 跨日状态必须累积**：阶段防抖（连续 N 日才切换）与「上一日趋势/建议」顺着日子传递，
  否则每天都是「第一天」，防抖规则形同虚设。检查点里连同 `stages` / `previous` 一起存，
  续跑后接着累积，不重置。
- **③ 出场价来自计划结构，不自己造阈值**：计划分支本身只带触发价（§5.11 的失效条件是文字），
  回放取「入场价下方最近支撑」作止损、「上方最近阻力」作止盈（§5.3 结构破坏口径）；
  取不到就只剩 `max_hold_days` 强平，并在 `exit_rules_missing` 里计数——**不加百分比止损**，
  那等于凭空造一条没经纸面回看的规则。
- **④ 组合层约束用保守近似**：同一标的已有未平回合时，后续触发不再建仓
  （`overlap_skipped`），避免同一段行情被重复计成多次暴露；资金曲线本身不建模，
  固定的 `PortfolioView` 意味着「资金耗尽后不再买」这类约束缺失，已写进 `not_modelled`。
  **实现要点**：这条规则必须按 `code` 分组——首版漏了过滤，一只标的的持仓会挡住全组合，
  10 只 × 460 天只剩 10 笔成交（增量 18 修复，回归测试 `test_overlap_is_scoped_per_code`）。
- **⑤ 大盘缺失如实标记**：不注入指数序列时 `market=None`，M1 环境档与「大盘 ≤ 警示」
  不会触发，结果偏乐观；`counters.market_missing_days` 按「真正跑过守卫链的日子」计数，
  不把「没跑成的日子」也算进去。
- 规模与续跑：一次运行只允许一套参数（参数网格请多次调用），`max_days` 截断并标
  `truncated`；`checkpoint_every` 落盘、`last_day` 保证已回放过的交易日不重复跑。
- 统计口径补了三个字段：`triggered` / `untriggered` / `open_positions`。原先
  `summarize_rounds` 的 `open` 把「未触发」也算进去，会让人误以为有一堆持仓没平。
- 真实数据实测（主库 `stock_daily` 经 `--import-main-db` 复制进 L1，601919 + 601818，
  2025-10-08 ~ 2026-10-22，`max_days=200`）：200 个交易日、399 次守卫链、184 条计划、
  164 个回合（触发 5、未触发 159），闭合 5 < 30 故只报计数不报胜率；`market_missing_days=200`
  如实标注，`exit_rules_missing=92`（那些回踩买点下方没有支撑位，只剩 max_hold）。
- 仍未做：参数网格并行、组合层资金曲线、分红、做 T、分级止损多档、大盘序列注入
  （接口已预留 `market_by_day`，但没有可靠的离线指数源，不硬编）。

### D-31 分红进模型：不复权序列的「除权当下跌 + 股息漏算」已补上

**问题**：回放用 L1 不复权日线（§4.6.4），而红利类标的每年除权 1–2 次。除权日价格会凭空
掉掉一个股息，后果有两层：① 股息是真实现金流入，序列里看不见 → 收益被低估；② 「跌了 6%」
其实只是除权，却按结构位止损打出去 → **误触发**。本样本 20 只在区间内共 103 次除权，
年化股息率 **5.1%**（占期初价 9.6%），这不是小数。

**做法**：`src/assistant/data/dividend.py` —— 把除权事件折算成**乘在除权日之前所有 K 线上的因子**
（前复权口径，锚在最新价），派生序列只在内存、不落库（§3.3 第 3 条）：

```
m = (P - c) / (k * (P - c * t))        P 除权前收盘、c 每股税前现金、k = 1 + 送 + 转、t 红利税率
```

推导：除权理论价 `P_ex = (P - c) / k`，持有 1 股的财富从 `P` 变成 `k*P_ex + c*(1-t) = P - c*t`；
要让派生序列的跨除权日涨幅等于这个财富比，只能把除权日之前的价格统一乘 `m`。`t=0` 时退化为
标准前复权因子。事件落 `assistant_dividend_event`（原始数据），复权序列不落库。

**踩到的口径坑（值得记住）**：东财 `RPT_SHAREBONUS_DET` 的 `BONUS_IT_RATIO` 是**送转合计**，
`IT_RATIO` 只是其中的转增。直接相加会把「纯转增」算成双倍——`10转3股派7.37元` 会被算成
送 3 + 转 3（因子 1.6 而不是 1.3），价格凭空多折 23%。现在按「送 = 合计 − 转增」拆分，
并用 `IMPL_PLAN_PROFILE` 文本对 20 只 × 区间内 103 条事件逐条交叉核对（**0 条不一致**）。

37.2%；紧止损（5–6%）显著更差，这条是稳的。

**决定（2026-11-27，已定，不再改口径）**：不改 `止损=最近支撑 / 止盈=最近阻力`。
理由三条：① 期望值统计上无差异，改了不赚钱；② 属 §5.11 语义变更（要立 R25、改需求正文、
改卡片上展示的止损位口径）；③ 唯一收益是降波动，而降波动更该在组合层（仓位/分批/同时持仓数）
解决，不必动单笔止损语义。反事实工具与 `--adjust` 口径保留，方法可随时重跑。
D-28 的「出场赔率」未决项**就此收口**。

**对 D-30 结论的影响**：胜率与单笔收益都上调，但**结论不变**——「含分红后仍跑不赢同期
买入持有」这一点没有翻转（同期等权买入持有本身也含分红，基准同样被低估，两边一起上调）。

**本地库注意**：`assistant_dividend_event` 是早前为 adj_factor 推算预留的表，旧库只有
`per_share` 等列，而 `create_all` 不补列。已在 `AssistantStore.create_all()` 里对这张表加
**追加列迁移**（只加缺的列、不删不改，非 SQLite 方言只告警不执行），并有用例
`test_old_schema_gets_columns_added` 钉住——否则老库第一次 `--dividends` 就会「no column」。

### D-32 板块三档真正进评分与 SEC-1（此前只有展示，结论层拿到的板块输入恒为 None）

**问题**：`sector_strength` 从增量 11 起就按 §4.6 算出来了（多日 2×2、三档 + degraded），
但它只写进 `assistant_sector_snapshot` 供展示。`pipeline` 调守卫链时既没传 `market=` 也没传
`sector=`，于是 `market_adjustment()` 永远走「数据缺失，按中性代入」，四项调整恒为 0——
**得分实际上只等于技术面分**，SEC-1 也永远不可能触发（`ctx.sector is None` → 只出 SEC-3 观察级）。

**这次接上的东西**：

| 环节 | 改动 |
| --- | --- |
| 大盘视图 | `pipeline.market_view(day)`：`MarketLine` → `MarketView`；指数当日未发布 → `regime_degraded`（只降置信度不改档）；宽度恒缺失并标 `width_degraded` |
| 板块视图 | `pipeline._sector_context(day)`：复用 D-22 的个股→板块映射，给出 `{代码: SectorView}`，同日只算一次 |
| `rs_t` 多日序列 | `_rs_history()`：按共同交易日逐日算「板块涨跌 − 大盘涨跌」，取最近 10 日；**单日值不得判连续**（§4.4），所以 SEC-1 只认这条序列 |
| 评分分值 | 板块从「乘权重」改为**可配置分值**：`sector_adj_up` / `sector_adj_down`（默认各 2 分），对应 §4.4 P0-4 的「可配置分值映射表」 |
| 版本 | `RULES_VERSION` → `rules-2.6.3`（同一套参数在接入前后得分必然不同） |

**为什么板块用绝对分值、大盘仍用比例**：两者共用 `w_market`(8 分) 这一份预算。大盘是 5 档
（强势/偏强/中性/偏弱/极弱）× 0.6~1.0，最多吃 4.8 分；板块若也乘权重，调 `w_market` 会同时
改两者的效果，没法单独调。改成「偏强 +2 / 偏弱 −2」的绝对分值后，板块与大盘各自可调，
合计仍裁剪到 `[-w_market, w_market]`（低权重维度不许吃掉技术面主导地位，§5.1）。

**±2 分的影响面（有数才敢定这个值）**：在 20 只红利 ETF 成分、460 个交易日、9200 个观测上
统计「分数距最近档位边界（80/62/40/22）的距离」：

| 距离 | 观测占比 | 含义 |
| --- | --- | --- |
| ≤1 分 | 11.5% | ±1 分最多影响这些观测的档位 |
| **≤2 分** | **23.3%** | **±2 分（当前默认）的跨档上限** |
| ≤3 分 | 34.5% | ±3 分会开始明显改写档位分布 |

23.3% 是**上限**（只有加减分方向与越界方向一致时才会跨档），且只影响「贴着边界」的观测；
`strong` 与 `bad` 两端的票几乎不受影响。所以 ±2 分是「能看出来但不改写评级结构」的量级。
参数仍标 `provisional=True`——§9.2 纸面回看没做，这个值只是有分布证据的初值。

**降级与缺失的处置**（三条都不许拿「没数据」当「板块弱」）：

1. 板块区未接入（关闭/一览失败/全部未映射）→ `sector=None` + `sector_mapped=True`，
   保持接入前的老行为（只出 SEC-3 观察级「快照缺失或降级」）；
2. 板块区有数据、但这只标的没映射上 → `sector_mapped=False` → SEC-3「映射失败（unmapped_holdings）」
   ——这是**更准确**的表述，比笼统说「缺失」有用；
3. 板块 `degraded=True` → 分值照给（档位是已有数据算出来的），但注记「仅注记不扣分」，
   另由 SEC-3 记数据质量。

**SEC-1 现在会真的触发**：`sector_strength=偏弱` 且 `rs_t` 连续 `risk_warn_consec_days`（默认 3）
日为负 → 警示级、`affects_advice=True`（限制加仓/新建仓）。本地用假板块源实测：
偏弱板块 + 连续 10 日负 → SEC-1「测试板块 板块偏弱且 rs_t 连续 10 日为负」。

**遗留（必须写清）**：**回放没有板块数据**。`ReplayConfig` 只吃个股 K 线与指数，
板块指数日线既没补进 L1 也没有注入点，因此 20 只样本的回放结果**不含板块加减分**
（`cv1` 已变，但 150 个闭合回合、62.7% 胜率与接入前完全一致，正说明板块分在回放里恒为 0）。
要让回测反映板块分，得先补板块指数历史（约 30–60 个板块 × 460 日），属下一步。

### D-33 板块指数日线进 L1，回放真正吃板块分（D-32 的「回放无板块」收口）

**为什么之前是 0**：`assistant_sector_daily` 是早前预留的表，只有 `pct_change` /
`up_count` / `down_count` / `lead_stock`——没有收盘价。板块三档要 20 日均线与 5 日斜率，
没有收盘价就只能一直 `degraded`+中性，于是回放里板块分恒 0（D-32 的遗留）。

**三层改动**：

| 层 | 改动 |
| --- | --- |
| 表结构 | `assistant_sector_daily` 追加 `open/high/low/close/volume/amount`；`create_all` 做追加列迁移（老库不用手改）。没有收盘价的老行**不返回**（不拿 0 冒充）；没有板块代码的板块**拒绝写入**（唯一键 `(sector_code, trade_date)` 缺一半会互相覆盖） |
| 取数 | `assistant_ingest_history.py --sectors`：东财 F10 → 同花顺板块名映射 → 逐板块补指数日线，映射落 `data/cache/assistant_sector_map.json`（回放读它，不联网）；另有 `--sector-names` / `--sector-refill` |
| 回放 | `SectorSeries`（建日期索引 + `bisect` 切片，只到 T）+ `sector_view_for_day`（三档 + 当日 `rs_t` + 近 10 日相对强度）；`replay(..., sector_by_code, sector_bars_by_name, index_bars)` |

**取数踩到的坑（比实现更值得记）**：同花顺 `stock_board_industry_index_ths` 内部按
`{year}.js` 逐年下载，某一年请求失败时它**自己 `continue` 掉、不抛异常**。2023–2026 一次
请求的结果：银行少 2023 全年 31 根、生物制品少 2024 全年 242 根，接口全部返回「成功」。
一份自洽却缺一年的序列，比取数失败更危险——三档会按「没有那一年」的样子平滑过去。
现在的做法：整体请求一次 → 对「结果里一根都没有的年份」逐年补一次（失败再重试一次）→
仍取不到才写日志并如实留缺。生物制品补回 733 根；银行 2023 年单独请求确为 0 行
（源头为空），保留 702 根并计入 `stats.sector.series` 的覆盖区间。

**回放侧的口径**（与实盘 `pipeline._sector_context` 对齐，差异如实写）：

1. **当日涨跌幅由序列自算**（今收/昨收−1）：回放没有板块一览历史，实盘用的是一览当日值。
   三档不用 `pct_change`，所以档位一致；`rs_t` 可能有尾差，已进 `not_modelled`。
2. **板块指数停在 T−1 就不给 `rs_t`**：`pct_change=0`、`rs_t=None`、`degraded=True`，
   三档仍按 T−1 序列判（§5.10 降级只注记不改档）。不拿昨天的差冒充今天。
3. **`history_rs_t` 取 10 日、末位用当日 `rs_t` 覆盖**：任一侧缺该日就不取那个差，不插值。

**结果（严格同口径对照：20 只、460 日、含分红 10% 税、同 `cv1-ed6c06831d`、20/20 全映射）**：

| 指标 | 无板块 | 带板块 |
| --- | --- | --- |
| 计划 / 回合 | 5203 / 4697 | 5024 / 4537 |
| 闭合回合 | 150 | 145 |
| 胜率 | 62.7% | **63.4%** |
| 单笔均净盈亏 | +2,810 | +2,821 |
| 盈亏比 | 1.36 | 1.33 |
| 净盈亏 | +421,524 | +409,036 |
| 研发（2025）胜率 | 66.7% | 66.7% |
| 验证（2026）胜率 | 58.7% | **60.0%** |
| 止损 / 止盈 / 强平 | 42 / 53 / 55 | 39 / 52 / 54 |

**关键发现：134 个重叠回合的净盈亏逐笔完全相同（差 0 元）**。差异全部来自
「16 笔不再触发、11 笔新触发」（前者 62.5%／+40,380，后者 72.7%／+27,892）——
即板块 ±2 分只改**入场门槛**（评分档位 → 建议 → 计划分支），不碰止损止盈价位。
所以它不会改善单笔收益结构，只会改变「参与哪几笔」。胜率 +0.7pp 与净盈亏 −3%
是同一件事的两面：挡掉的 16 笔里赚钱的居多，换进来的 11 笔胜率高但单笔总额小。
20 只里 10 只受影响（000423、000538、002415、002558、600012、600211、600295、
601009、601077、601872 的净盈亏有变化），其余逐笔一致。

**覆盖面**：板块视图 9200 个 code-day（20 只 × 460，缺失 0）——偏强 3972／偏弱 3310／
中性 1918／降级 0。

**映射收口到 20/20（新增显式别名表）**：原先 5 只未映射全是「同词异序/带后缀」，
精确匹配不命中：

| 代码 | 东财行业 | 同花顺板块 |
| --- | --- | --- |
| 600012 | 铁路公路 | 公路铁路运输 |
| 600188 / 601101 | 煤炭开采 | 煤炭开采加工 |
| 601872 / 603565 | 航运港口 | 港口航运 |

处理方式是 `SECTOR_ALIASES` 这张**三条目的穷举表**（不是相似度匹配）：精确名不中时
查一次，命中即用同花顺名（回放要按名字取序列）。**刻意不用 `difflib`/编辑距离**——
相似度会把「煤炭开采」错配到别的板块，而板块错配比未映射更危险；表里没写的一律不猜，
`test_alias_does_not_guess_beyond_the_table` 把这条钉住。别名命中会留日志，出问题时
能一眼看出是哪条规则接上的。

**`RULES_VERSION` 不 bump**：规则没变（板块分逻辑在 2.6.3 已进指纹），变的只是回放多了
一份数据源。代价是同一 `calc_version` 下的回放结果会随数据补齐而变——所以
`stats.sector.series` 逐板块记「根数 + 起止日」，让「规则没变、数据变了」可辨认。

**仍未建模**：板块 2×2 阈值（20 日线/5 日斜率/0.5% 缓冲带）仍是 `SectorStrengthParams`
默认值，没进参数注册表；回放不含板块宽度与领涨股；板块指数历史只有同花顺单一来源
（无备源，取不到就是缺）。
